## 0. なぜこのルールが要るのか（2案件の実測）

同じ人・同じ時期・同じ規模の2案件で、手戻りの量がはっきり分かれた。

| | A案件（アニメ主体のLP） | B案件（観光サイト） |
|---|---|---|
| 総コミット | 78 | 68 |
| **選択肢（案・比較mock）を出したコミット** | 9（**12%**） | 27（**40%**） |
| **同じ箇所を繰り返し直したコミット** | **4** | 1 |
| 「◯回目でやっと解決」した不具合 | 真っ白3回 / 切替の違和感4回 / 巻き添え削除3回 | ほぼ無し |

**差は能力でも真面目さでもない。「決まっていないことを、誰が決めたか」だけ。**

- B案件は、決められないことを**案とmockと調整パネルにして本人に渡した**
- A案件は、決められないことを**Claudeが決めて、決めたことを言わなかった**

そしてB案件のコミットには、こういう記述が実際に残っている。

> 「黒目位置だけはカンプから取れないので**暫定値**。`/mock/face` で調整する」
> 「本番は**暫定で**カード案1+ボタン案1を適用（タイトルは**仮名**）」
> 「カンプと**意図的に揃えていない点は報告済み**（板の影・環境音ボタン…）」

**推測して埋めた点は、B案件にも同じだけある。違うのは「言ったか、黙ったか」だけ。**
つまり事故の原因は推測そのものではない。**黙ったこと**である。

## 1. 大原則（この3つが全部）

### 原則1: 推測は歓迎。**黙るのが禁止。**

止まって聞いてばかりでは仕事にならない。**推測して進めるのは良いこと。**
ただし、**推測した瞬間に、それが推測だと分かる形にすること。** 例外なし。

| ❌ 禁止 | ✅ 正しい |
|---|---|
| 取れなかった値をそれっぽく埋めて黙る | 「ここは取れなかったので◯◯と仮置きしました」と書いて進む |
| 「カンプ通りにしました」だけの報告 | 「◯◯と△△は取れなかったので仮置き。他はカンプ通り（表）」 |

### 原則2: 決まっていないことに気づけるのは、Claude 側だけ

ヒデさんは非エンジニアで、**「何が決まっていないか」は画面を見ても分からない。**
「聞かれていない＝全部決まっている」と受け取る。

→ **決まっていない箇所を見つけるのは Claude の仕事。見つけたら、こちらから聞く。**
気づいたのに黙って埋めるのは、**気づかなかったより悪い**。

### 原則3: 判断を止めない。**仮置きして進み、仮置きを見せる。**

質問のために作業全体を止めない。
**答えに依存しない部分は全部やり切る。** 依存する部分だけ仮置きして、最後にまとめて見せる。

## 2. 塩梅の決め方（信号機）

「聞くか・勝手に決めるか」は感覚で決めない。**3つの問いで機械的に判定する。**

1. **正解が1つに決まるか？**（技術的に決まる／好みで変わる）
2. **見た目・体験に出るか？**（画面で見えるものか／中身だけか）
3. **あとで変えるのは安いか？**（1行直せば済む／全体に波及する）

| 判定 | 条件 | どうする |
|---|---|---|
| 🟢 **黙って進める** | 正解が1つに決まる **かつ** 見た目に出ない | 報告に1行書けば十分 |
| 🟡 **仮置きして進む** | 見た目に出るが、**あとで安く変えられる** | **必ず「仮置き」と明示**して進む |
| 🔴 **手を止めて聞く** | 好みで変わる **または** あとで変えるのが高い | 選択肢を作って聞く |

### 具体例（両案件で実際にあったもの）

| 場面 | 判定 | 理由 |
|---|---|---|
| 変数名・関数の分け方・リファクタ | 🟢 | 見た目に出ない |
| 明らかなバグの修正 | 🟢 | 正解が1つ |
| 同じ値の二重管理を1か所にまとめる | 🟢 | 見た目が変わらない |
| **カンプから取れなかった数値**（字間・行間・座標） | 🟡 | **取れなかったと明示して仮置き** |
| カンプに無い状態（hover / 空 / エラー / 読み込み中） | 🟡 | 補完案を明示して進む |
| レスポンシブ（カンプが1〜2枚しかない） | 🟡 | 規則を書いて仮置き。規則が立たない時は🔴 |
| アニメの秒数・イージング・間合い | 🟡→🔴 | **触れるものを出せるなら🔴（案を出す）** |
| 演出そのもの（どう動くか） | 🔴 | 好みで変わる。案を作って選んでもらう |
| 色・書体・トーンの変更 | 🔴 | ブランドの判断 |
| ページ構成・セクションの追加削除 | 🔴 | 手戻りが高い |
| **資料同士が食い違っている**（カンプ vs 絵コンテ vs 口頭） | 🔴 | 両方並べて、どちらを採るか聞く |
| **カンプの明らかなミス**（はみ出し・誤字・値のバラつき） | 🔴 | **黙って直さない。** 意図かもしれない |
| 4,000行超のファイルの構造変更 | 🔴 | 波及が大きい |

### 🟡 が多くなりすぎた時は、🟡 をまとめて 🔴 にする

仮置きが**5件を超えたら**、個別に進めず**一度まとめて確認**する。
仮置きだらけの状態で先へ進むと、土台が違っていた時に全部やり直しになる。

## 3. 🟡の作法 ——「仮置き」の見せ方

推測して進めてよい。**ただし3か所に痕跡を残す。**

### ① コードに印を付ける

```js
// 仮置き: カンプから取得できず。0.6s / ブラー付きで補完（要確認 2026-08-16）
const REVEAL_DUR = 0.6;
```

### ② 報告に「仮置き一覧」を出す（最重要）

作業報告の最後に、**必ずこの表**を付ける。無い報告は未完成とみなす。

| 箇所 | なぜ決められなかったか | いま入れた値 | 変えるコスト |
|---|---|---|---|
| 見出しの出る速さ | カンプは静止画で秒数の指定が無い | 0.6秒・ブラー付き | 小（1行） |
| 幅2000pxの時の画像 | カンプ2枚で規則が一致しない | 右端683px固定 | 中（計算式ごと） |

### ③ 会話の最後に「見てほしいのはここ」を3つ以内で言う

全部を確認してもらおうとしない。**判断が要るものだけを絞る。**

## 4. 🔴の作法 —— 聞き方のルール

### ✅ やること

| ルール | 理由 |
|---|---|
| **選択肢＋おすすめ＋理由**で聞く（`AskUserQuestion` を使う） | 「どうしますか？」は考える仕事を丸投げしている |
| **まとめて聞く。1回3〜5問まで** | 細切れの確認は、それ自体が作業の邪魔になる |
| **見た目のことは言葉で聞かない。触れるものを出す** | 秒数・間合いは文章では判断できない（→ 下記） |
| **聞いている間も止まらない** | 答えに依存しない部分は進めておく |
| **前提を書いてから聞く** | 「こう解釈しました。違ったら言ってください」 |

### ❌ やらないこと

- 「どうしますか？」だけの丸投げ
- 3往復以上かかる細かい確認（それは🟡にして仮置きで進む案件）
- 全部の仮置きを確認対象にする（判断が要るものだけ）
- 一度決まったことを蒸し返す

### 見た目・動きは「触れるもの」を出して聞く

これがB案件の手戻りが少なかった最大の理由。**言葉で合意しようとしない。**

| 出すもの | どんな時 |
|---|---|
| **比較mock（3〜5案）+ 一覧ページ** | 演出そのものが決まっていない時 |
| **調整パネル**（[tune-panel](https://github.com/hideyuki-yamanaka/tune-panel)） | 方向性は決まっていて、数値だけ詰める時 |
| **設定ファイルに切り出す** | あとから何度も触りそうな値 |

採用が決まったら**不採用のmockはすぐ消す**（残すと重くなる・どれが本番か分からなくなる）。

## 5. 着手前に必ず出すもの ——「決まっていない表」

**実装を始める前**に、この表を出す。ここが最大の事故防止装置。

| 項目 | 資料から取れた | 取れなかった → こう決めた（要確認） |
|---|---|---|
| 見出しの書体・サイズ | SF Pro Text 200 / 50px | — |
| 見出しが出る速さ | — | **0.6秒・ブラー付き** |
| 画面幅を変えた時 | — | **右から120px固定（カンプ2枚から推定）** |

**右列こそが行き違いの発生源。** ここだけ先に見てもらえば、手戻りの9割は着手前に潰せる。

> 資料は「止まった絵」しか決めていないことが多い。**動き・間合い・順番・hover・
> 画面幅を変えた時・エラー時**は、たいていどこにも書かれていない。
> それでも実装はそこを埋めないと動かない。**だから必ず埋める。だから必ず言う。**

## 6. 絶対にやらないこと（5つ）

1. **取れなかった値を黙って埋める** ← 一番やってはいけない
2. **「◯◯通りにしました」だけの報告**（数値の表と実測値で示す）
3. **目視で「確認しました」と言う**（書体・字間・余白は目で見て分からない）
4. **同じ症状に3回目の対処をする**（2回出たら対処をやめて原因を探す）
5. **好み・ブランドの判断を勝手に確定させる**（仮で置くのは可。確定は本人）

## 7. 傾向と対策（まとめ）

| 傾向（実際に起きたこと） | 対策 |
|---|---|
| 資料が決めていない領域ほど事故る（動き・間合い・レスポンシブ） | 着手前に「決まっていない表」（5章） |
| 選択肢を出した割合が低い案件ほど手戻りが多い（12% vs 40%） | 見た目は触れるものを出して聞く（4章） |
| 推測そのものではなく、**黙ったこと**が事故になっている | 仮置きの3点セット（3章） |
| ヒデさんは「何が決まっていないか」に気づけない | 気づいた側（Claude）から聞く（原則2） |
| 症状だけ直すと3〜4回繰り返す | 2回目で原因調査へ切り替える（6章-4） |
| 巨大ファイルの範囲置換で巻き添え削除 | 置換マーカーは同じセクション内 / 4,000行超で分割提案 |

## 9. 再発防止の4ルール（2026-08-30 白書から制定）

8月の全560コミットの棚卸し（バイブコーディング白書）で見つかった
「直したのに直っていない」への構造対策。過去の症状一覧は [FIXLOG.md](FIXLOG.md)。

### ルールA: 「変わってへん」再発テスト 🔴最重要

見た目・既定値を変える修正は、報告する**前に**必ず:

1. 値が住める場所を**全部**機械検索する
   （① コードの既定値 ② 焼き込み設定・SHIPPED系ダンプ ③ ブラウザ保存値(localStorage)
   ④ 案・プリセットごとの保存値 ⑤ migrationフラグ）
2. **古い保存値をわざと注入**した状態（＝ヒデさんの環境の再現）を作る
3. **リロード2回**して新しい見た目が維持されるかを実測する
   （migration の書き戻し漏れは「1回目だけ直って見える」ので、2回目が必須）

まっさらな環境だけで確認して「直りました」と言うのは禁止。

### ルールB: 「確定」と言われたらパネルから畳む

ヒデさんが「これで確定」と言った仕様は、その場で調整パネルの項目を削除して
固定値1つにする（層が減る＝ルールAの対象も減る）。
残したい特別な理由がある時だけ、理由を添えて「残しますか？」と提案する。

### ルールC: 不具合は FIXLOG.md に1行残し、修正前に必ず検索

- 不具合を直したら [FIXLOG.md](FIXLOG.md) に1行追記（日付 / プロダクト / 症状 / 真因）
- 新しい不具合の修正に入る**前に**、FIXLOG を症状の言葉で検索する
- 同じ症状が過去にあれば、**対処せず最初から原因調査モード**に入る
  （「同じ症状2回ルール」をセッションの壁を越えて効かせる仕組み）

### ルールD: 「ここ」の解釈を1行宣言してから直す

「ここを直して」と言われたら、確認待ちはせず
**「『ここ』＝◯◯と解釈して進めます」と先頭に1行だけ宣言**して着手する。
狙い違いをヒデさんが作業中に発見できる。返事は待たない（止まらない）。
