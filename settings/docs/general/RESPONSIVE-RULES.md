# レスポンシブ実装ルール（SP を "別のカンプ" として実装する／途中で幅が変わっても崩れない）

> 🔴 **着手前に必ず読む。** [DESIGN-SYSTEM-RULES.md](DESIGN-SYSTEM-RULES.md) の「スペック表ゲート」を
> **各ブレイクポイントに対して個別に**適用するための追補。2026-09-09、anyflow v3 のスマホ対応で
> 「カンプを無視した実装」「実機だけ崩れる」が多発したため制定。根拠の実測は
> [../anyflow/project(このセッションの作業ログ)] と [FIXLOG.md](FIXLOG.md) の 2026-09-09 の行。

## 🔴 全プロダクト共通の基準（2026-09-26 ヒデさん指定「柔軟なレスポンシブをベースに」）

> **どんな端末・どんな窓の幅でも、途中で幅を変えても（窓のドラッグ・スマホ/タブレットの回転）崩れないこと。**
> **合格ライン＝「A の幅で開いて B の幅へ変えた画面」が「最初から B の幅で開いた画面」と部品単位で一致すること。**
> 作り方と確かめ方は **6章**。新しく作るものは「CSS だけで切り替える」を第一選択にする。

## 0. なぜ "前も立てたルール" がレスポンシブで無視されたか（真因）🔴最重要

ヒデさんの指摘：**「デザインカンプを無視して実装し続ける。前もルールを立てたのに、レスポンシブの時だけ無視される」**。

真因は **「SPを"新しいカンプの実装"ではなく"既存(PC)実装の微調整"だと分類してしまう」** こと。

- PC は「カンプ → コード」と認識するので [DESIGN-SYSTEM-RULES.md](DESIGN-SYSTEM-RULES.md) の
  **スペック表ゲート（コードより先に全ノードの表を作る）** が発火する。
- SP は**中身(テキスト・要素)が PC と同じに見える**ので、脳が「既存 CSS を目分量で寄せるだけ」と
  分類し、**ゲートが発火しない**。結果、PC の値を持ち込んだり、`get_metadata` の枠サイズから逆算したりする。

### だから、この1行を大原則にする

> **SP(や各ブレイクポイント)のカンプは、PC とは別の完全な実装対象。**
> **「調整」ではなく「もう1つのカンプを一から実装する」。だからスペック表ゲートも breakpoint ごとに必ず通す。**

SP フレームは **独立したノードID・独立した Fill/Hug/Fixed・独立したフォントサイズ/色**を持つ
（anyflow なら PC=別フレーム / SP=`16534:22140`）。**PC の値を SP に一つも持ち込まない。**

## 1. レスポンシブ着手時の必須ワークフロー（この順番・例外なし）

1. **対象ブレイクポイントのカンプフレームを特定**（SP なら SP フレームのルートノードID）。
2. **そのフレームの全ノードを Plugin API で吸い出す**（`use_figma` で `layoutMode` /
   `layoutSizingHorizontal|Vertical`(Fill/Hug/Fixed) / `itemSpacing` / `padding` / x/w/h、
   テキストは `getStyledTextSegments(['fills','fontName','fontSize'])` で**文字ごとの色・書体**）。
   - ⚠️ `get_metadata`(枠サイズ)だけで判断しない。`get_screenshot`(フラット画像)だけで色を判断しない。
     → 今回「つなぐ/強み」のグラデの有無をスクショで誤判断し、後で `getStyledTextSegments` で
     **全文字が単一色 #101828(グラデ無し)** と確定して直した。文字色/塗りは必ずセグメントで読む。
3. **SP 用スペック表を作る**（PC の表とは別物）。列は DESIGN-SYSTEM-RULES と同じ
   （書体/ウェイト/サイズ/行間/字間/色/線幅/角丸/影/padding/margin/gap/幅高さ/**Fill・Hug・Fixed**/整列）。
4. **表にある値だけをコードに書く。** SP カンプに無い値は **「仮置き」と明示**して進め、5件超で一度確認。
   - ❌ PC の値をスケールして推定する（例: PC の Platform 50px を「モバイルは適当に小さく」）。
   - ❌ 枠の幅からフォントサイズや字間を逆算する。
5. **実装後、computed で実測して表に ✅/❌。** ❌が残る間は「完了」と言わない。

### Fill/Hug/Fixed を必ず読む理由（今回の実例）

- Point 1/2 の枠を「328px 固定」と**推測**していたが、Plugin API で読むと **枠 342 / 子は Fill**。
  → 左右24pxの全幅が正しかった。**幅は px ではなく Fill/Hug/Fixed の意図で決める。**
- Fill の要素に固定 px を入れると、別の画面幅で必ずズレる。

## 2. 実機検証マトリクス（エミュだけで「直った」と言わない）🔴

今回の最大の落とし穴：**ヘッドレスの縦長ウィンドウでしか検証せず、実機(iOS Safari)で崩れた**。

- iOS Safari は上下バーで **innerHeight が設計値より 150〜170px 小さくなる**（iPhone 16 Pro 実測 ~700）。
- 「高さも縮小条件に入る」スケール(`--sp`)を使っていたため、**ビジョンだけ実機で ~90% に縮小**。
  縦長エミュ(844/1480)では `--sp=1` で再現せず、「直りました」と誤報告した。

### 検証する画面サイズ（必ず全部）

| 幅 × 高さ | 何を見るか |
|---|---|
| 402 × **700** | 実機相当(アドレスバー有)。**ここで崩れないことが本番の合格ライン** |
| 402 × 844 | アドレスバー無し |
| 390 × 660 | 小さめ端末 + 短い高さ |

- **合否1: 横スクロールが出ていないか** … `document.documentElement.scrollWidth === innerWidth`。
- **合否2: 左右の余白** … 代表要素の `left≈24 / right≈(幅-24)` を実測（今回の設計は左右24px）。
- **合否3: スケールが高さで変わらないか** … 上の3サイズで**主要要素のサイズが同一**であること
  （高さを変えたら文字が縮む＝高さ基準スケールのバグ）。
- **合否4: 本番URLを実機設定で描画** … localhost だけでなく、デプロイ後の本番URLを
  iPhone UA/解像度で1回描画して確認。

### iOS Safari 固有チェック（Chromium で再現しない事象）

- **blur フィルタ**は合成レイヤーの残像(=影/消失)になりやすい。小さなUI(ロゴ/ボタン/サブコピー)の
  entrance blur はモバイルで **0 に**（フェード+移動は可）。大きなグラフィックの登場ブラーは可。
- **CSS animation** は `overflow:hidden` + `transform` 配下で iOS だと落ちて「消えたり出たり」する
  ことがある。ただし今回の真因は **rv() が inline に書いた blur** だった。まず inline を疑う。
  JS 毎フレーム駆動に逃げると**重い描画ループと競合してガタつく**ので、原則 CSS animation に戻す。
- **アドレスバー開閉**で innerHeight だけ変わる → それを拾って再レイアウトすると中身がガクつく。
  **モバイルは幅が実質不変(±2px)なら再レイアウトしない**。

## 3. スケールと幅は "対" で動かす（今回の overflow の教訓）

固定キャンバス方式（`stage { width: 幅; transform: scale(倍率) }`）では、
**倍率(scale)と土台の幅(width)は同じ基準から算出される対**。片方だけ変えると必ずはみ出す/縮む。

- 今回 pin-stage の scale を「高さ込み(`--sp`)」→「幅のみ(`--s`)」に変えたが、
  **width は高さ込み(`--swp`)のまま**にした。実機で width 448px × 等倍 = 画面(402)からはみ出し。
  → **width も幅のみ(`--sw`)に揃えて解決。**
- 原則：**モバイルの静的レイアウトは "幅のみ" でスケールする**（下にスクロールできるので高さ制約は不要）。
  scale も width も**同じ "幅のみ" 基準**で統一する。

## 4. デプロイ/キャッシュで時間を溶かさない

「本番に反映されない」の切り分けは**最初に30秒で**やる。

1. `curl -s "本番URL/?nocache=$RANDOM" | md5` と `curl -s 本番URL | md5` と `md5 ローカル` の**3者一致**を見る。
   一致すれば**オリジンは最新**＝原因はコードでなく配信/端末キャッシュ。
2. `curl -sI 本番URL` で `x-vercel-cache: HIT` かつ `age` 増加なら**CDNエッジがHTMLをキャッシュ**。
   `vercel.json` に `CDN-Cache-Control: no-store` を足す（HTMLは毎回オリジン＝最新に）。
3. 実機は `?v=2`(数字を毎回変える)で開くのが一番確実にキャッシュを飛ばせる。

## 6. 途中で幅が変わっても崩れない作り（2026-09-26 制定・全プロダクト共通）

### 6-1. 何が起きるか（ヒデさん向けのたとえ）

ページが **開いた瞬間に「PC 用の衣装」か「スマホ用の衣装」を着せて**、文字の大きさなどを決める作りだと、
途中で窓の幅を変えた時に **部屋(並び方)だけ入れ替わって衣装はそのまま** になる。
→ PC 用の大きい文字がスマホの幅からはみ出す、など。**最初からスマホ幅で開くと綺麗なのに、途中で狭めると崩れる**のはこれ。
本物のスマホでも **横向きにすると幅が境目を超える**ので同じことが起きる。

- 実例（anyflow V5・2026-09-26）：境目 600px。開いた時に ①スマホ用の値を設定そのものへ流し込む ②パネルで調整した文字の
  大きさを各文字に書き込む ③見出しの改行位置を1回だけ決める、をしていたため、窓を狭めると 40px の見出しが 390px 幅にはみ出した。
  さらに **スマホ幅で開くと「案の上書き控え」がスマホの値で保存され、あとで PC で開くとスマホの値が混ざる**不具合も出ていた（[FIXLOG](FIXLOG.md) 2026-09-26）。

### 6-2. 作り方の優先順位（上から選ぶ）

1. **CSS だけで切り替える（新しく作るものの基本）**
   - `@media`・`clamp()`・`%`/`vw`/`fr`・コンテナクエリなど、**ブラウザが幅に合わせて自動で切り替える書き方**にする。
   - これなら途中で幅を変えても何もしなくてよい（開き直し不要）。**まずこれで作れないかを考える。**
2. **JS で PC/スマホ別の値を書き込む場合は、境目をまたいだ時に書き直す**
   - `matchMedia('(max-width: 境目px)')` の `change` イベントで、書き込んだ値（inline style・文字の大きさ・改行など）を**全部書き直す**。
   - 書き直す所が少なく、全部を洗い出せる時だけ選ぶ。
3. **状態が複雑なら「境目をまたいだら自動で開き直す」（anyflow V5 がひな形）**
   - 設定そのものに値を流し込んでいる／開いた時に1回だけ決める所が多い／取りこぼしが怖い、なら**開き直すのが確実**
     （開き直す＝「最初からその幅で開いた」と必ず同じになる）。
   - ひな形：`anyflow/v5/js/parts/06-sections.js` の `modeSwitchReload` / `restoreModeReloadPos`。守る要件：
     - 幅が落ち着いてから（**0.4 秒待って**）**1 回だけ**開き直す（ドラッグ中に何度も開き直さない）
     - **またいですぐ元の側へ戻したら取り消す**（開いた時の側を記録しておき、そこへ戻ったらやめる）
     - **見ていたセクションの同じ位置へ戻す**（sessionStorage にセクション id と進み 0〜1 を入れて、読み込み後に戻す）
     - **4 秒以内の再発は止める**（万一の往復ループ防止）
     - パネルのスマホプレビューなど**幅が固定の枠の中は対象外**
     - **開き直すまで保存を止める**（下の 6-4）

### 6-3. 境目の決め方

- 境目の数字は **1 か所の定数**にし、CSS の `@media` と JS の `matchMedia` で**同じ値**を使う（anyflow は `MOBILE_MAX = 600`）。
- `innerWidth` だけで判定しない（iOS Safari は読み込み直後に 980px 等を一瞬返すことがある）。`matchMedia` を基準にする。
- 判定は**使うたびに**行う。ファイルの一番上で `const X = matchMedia(...).matches` のように**開いた時の値で固定しない**
  （固定するなら 6-2 の ②か③で必ず面倒を見る）。

### 6-4. スマホ判定の間は、どこにも保存しない

- スマホ用の値を設定に流し込んで描いている間に保存すると、**PC の保存値がスマホの値で上書きされる**。
- **本体の設定・案の控え・プリセットなど、保存先は全部**止める（anyflow は `save()` と `presetStoreSave()` の冒頭で `isMobile` を見て抜ける）。
- 新しい保存処理を足す時は、**必ず同じ止めを入れる**。境目で開き直す直前も保存しない（`window.__afModeReloading`）。

### 6-5. 確かめ方（完了の条件・🔴「直りました」はこれを通してから）

| 確かめること | やり方 | 合格 |
|---|---|---|
| 狭めた時 | PC 幅(1440×900)で開く → 390×844 へ変える | 最初から 390×844 で開いた画面と部品単位で一致・はみ出し 0 |
| 広げた時 | 390×844 で開く → 1440×900 へ変える | 最初から 1440×900 で開いた画面と一致 |
| 境目をまたがない | 1440 → 1100 など | 何も起きない（開き直さない） |
| すぐ戻す | 390 へ変えて 0.2 秒で 1440 へ戻す | 何も起きない |
| 見ていた位置 | 真ん中のセクションを見ながら狭める | 開き直した後も同じセクション |
| スマホを横向き | 390×844 → 844×390（タッチ端末として） | 横向きの幅の見た目になる |
| 保存値 | スマホ幅で開いて広げた後の保存値 | 最初から PC で開いた時と完全一致 |

- 代表の幅：**390×844・844×390（スマホ縦/横）・768×1024・1024×768（タブレット）・1280×760（縦が短いノートPC）・1440×900・1920×1080**。
- 比べ方の道具：Playwright で「開く→`setViewportSize`→（開き直しを待つ）→測る」と「最初からその幅で開いて測る」を並べ、
  要素ごとの位置・大きさ・computed style を比較する（anyflow の scratchpad `fp.mjs` の `FROM_PC`/`FROM_SP` と同じ考え方）。
- 報告は「直りました」ではなく**表と実測値**で（[WORKING-RULES.md](WORKING-RULES.md)）。
