このファイルをリポジトリに置くか、内容をそのまま貼れば同じ品質基準で動く。

> 🧭 **推測してよい範囲・聞くべき場面・仮置きの見せ方は [WORKING-RULES.md](WORKING-RULES.md)**（対になるファイル）。

> 原因は毎回同じで、**取れなかった情報を推測で埋め、それを報告しなかった**こと。

---

## 大原則（これだけは絶対）

1. **推測で埋めない。** カンプから取れなかった値は、勝手に決めない
2. **取れなかったことを黙らない。** 「取れなかったので、こう仮定した」と必ず言う
3. **「カンプ通りにしました」だけの報告は禁止。** 数値の表と実測値で示す

この3つが守られていれば、多少手戻りしても事故にはならない。

## 0. スペック表ゲート（コードを書く前に・例外なし）🔴 2026-08-30 追加

> 追加の理由: このファイルの制定後も「ウェイト・サイズ・レイアウト・スペーシング・線幅・色が
> カンプと違う」が繰り返し起きた（8月の振り返り白書で確認）。ルールを知っていても、
> 実装の瞬間に**スクショの見た目や記憶から CSS を書いてしまう**のが直接原因。
> だから「後で照合する」ではなく、**先に表を作らないと書けない**手順に変える。

### 手順（この順番を崩さない）

1. **コードを書く前に**、対象範囲の全要素について「スペック表」を作る
   （行＝要素、列＝書体 / ウェイト / サイズ / 行間 / 字間 / 文字色 / 塗り / 線の色 /
   **線幅** / 角丸 / 影 / padding / margin / **gap** / 幅・高さ / Fixed・Hug・Fill / 整列）
2. 値の出どころは **`get_design_context` のみ**。スクショの目測・記憶・
   「よくある値」（400 / 16px / #333 / 1px …）で書くのは**全部推測＝禁止**
3. コードに書いてよいスタイル値は2種類だけ:
   **① スペック表にある値** ② 「仮置き」と印を付けた値（→ WORKING-RULES の🟡作法）
4. 実装後、`getComputedStyle` で**実測**し、表に「実装値」「判定 ✅/❌」列を足して報告する
5. **❌が1つでも残っている間は「完了」と言わない**

> 🔴 **レスポンシブ(SP/ブレイクポイント)は特に飛ばしやすい。** 中身が PC と同じに見えるので
> 「既存CSSの微調整」と誤分類してこのゲートを飛ばしがち。**SP は "別のカンプの一からの実装"** として
> ゲートを breakpoint ごとに必ず通す。詳細と実機検証マトリクスは
> [RESPONSIVE-RULES.md](RESPONSIVE-RULES.md)（2026-09-09、anyflow スマホ対応の事故から制定）。

### 小さい修正でも省略しない

1要素の追加・微修正でも、その要素の1行分の表は作る（30秒で済む）。
8月にズレが出たのは大きな実装よりむしろ「ついでの小さい追加」だった。

## 1. 何を照合するか（デザインシステム全項目）

「フォント」だけではない。**下記すべて**がカンプの規定対象。
実装前に該当する項目を洗い出し、実装後に1件ずつ照合する。

### タイポグラフィ
- 書体ファミリー（⚠️ **光学サイズ違いに注意**。SF Pro には Text と Display があり、
  Display は字幅が狭く線も細い。Noto Sans JP にも Thin/ExtraLight/Light が別々にある）
- ウェイト 🔴 **呼称→数値の変換はフォントごとに違う。必ず下の対応表を引く（2026-09-01 制定）**

#### ウェイト呼称→数値の対応表（推測禁止・ここを引く）

> 事故例: カンプの「SF Pro Text : Ultralight」を、Noto の感覚（Thin=100）のまま
> 「Ultralight は Thin の隣だから 200」と推測で埋め、数値が1段太くなった（2026-09-01 発覚）。
> **「Thin」と「Ultralight/ExtraLight」の順序が Apple 系と一般系で逆**なのが罠。

| 数値 | Apple系（SF Pro / SF Pro Text / SF Pro Display / Helvetica Neue） | 一般系（Noto Sans JP / Google Fonts の大半 / CSS標準名） |
|---|---|---|
| **100** | **Ultralight** | **Thin** |
| **200** | **Thin** | **ExtraLight（UltraLight表記もある）** |
| 300 | Light | Light |
| 400 | Regular | Regular / Normal |
| 500 | Medium | Medium |
| 600 | Semibold | SemiBold |
| 700 | Bold | Bold |
| 800 | Heavy | ExtraBold |
| 900 | Black | Black / Heavy |

#### 変換の手順（この順番・スキップ禁止）
1. カンプから **font-family を先に確定**する（呼称より先。同じ呼称でも数値が変わるため）
2. そのファミリーで上の表を引いて数値化する。**表に無いファミリーは推測せず**、
   公式のウェイト一覧を Web で確認するか、ヒデさんに確認する
3. スペック表には **「呼称(数値)」を併記**する（例: `SF Pro Ultralight(100)`）。
   数値だけ・呼称だけの記載は禁止（検算できない）
4. 実装後、`getComputedStyle(el).fontWeight` の**実測値がスペック表の数値と一致**するまで「完了」と言わない
- サイズ / 行間 / 字間 / 字下げ / 揃え（左・中央・右・両端）
- 大文字小文字変換、装飾（下線・打ち消し）
- 色（不透明度込み）

### カラー
- 塗り / 線 の色、**不透明度**、**ブレンドモード**
- グラデーション: 種類（線形・放射・角度）、**角度**、**各ストップの位置と色**
- 変数・スタイル名（デザイントークンがあれば名前ごと写す）

### スペーシング
- padding（上下左右それぞれ）
- margin / 要素間の距離
- **gap**（オートレイアウトの間隔。行・列で別々のことがある）

### サイズ・レイアウト
- 幅 / 高さ / 最小・最大
- **固定か可変か**（Figma の Fixed / Hug / Fill）。ここを取り違えると
  画面幅を変えた時だけ崩れる
- オートレイアウトの方向・整列・分配・折り返し
- 制約（Constraints: 左寄せ / 右寄せ / 中央 / 伸縮）→ **レスポンシブの挙動が決まる**
- 重なり順（z）

### 角丸・線
- 角丸（**4隅が別々**のことがある）
- 線の太さ / 色 / 位置（内側・中央・外側）/ 破線

### 効果
- ドロップシャドウ / インナーシャドウ（x, y, ぼかし, 広がり, 色, 不透明度）
- レイヤーブラー / 背景ブラー（backdrop-filter）
- 複数掛かっている場合は**全部**

### その他
- 不透明度、マスク、クリップ、回転、反転
- 画像の収まり方（cover / contain / 位置）

## 2. どう取るか（ツールの使い分け）

| 欲しい情報 | 使うツール | やってはいけないこと |
|---|---|---|
| 書体・ウェイト・サイズ・字間・行間・色・角丸・影・padding・gap | **`get_design_context`**（CSS/コードとして文字列で返る） | ❌ 目視や逆算 |
| ノードの一覧・階層・位置・サイズ | `get_metadata` | ❌ ここからフォントを推測する |
| ベクター座標・グラデの実数値 | SVG 書き出し（`download_assets`） | ❌ SVG から文字情報を読む |
| 見た目の確認 | `get_screenshot` | ❌ スクショだけで数値を決める |

### ⚠️ 実際にやらかした2つの罠

**罠1: `get_metadata` の「テキスト枠の幅」から字間を逆算した**
枠の幅はデザイナーが手で広げていることがあり、**文字送りとは無関係**。
これを字間と誤読して `letter-spacing: 0.178em` を入れ、全体が間延びした。
→ **フォント関係は必ず `get_design_context`。**

**罠2: SVG 書き出しで図を作ったら、中の文字情報が消えていた**
SVG では文字がパスに変換されるため font 情報が失われる。
見た目が合っていたので確認を怠り、書体もウェイトも間違っていた。
→ **図の中の文字も、別途 `get_design_context` で取る。**

## 3. 照合の手順

1. **全ノードを列挙する。** セクション単位で、テキスト・図形・画像を漏れなく数える
2. **カンプにあって実装に無いもの / 実装にあってカンプに無いもの**を洗い出す
   （実際に「認証基盤」というラベルが丸ごと抜けていた）
3. 各項目を `get_design_context` で取得
4. 実装側は**ブラウザで実測**（`getComputedStyle` / `getBoundingClientRect` /
   `canvas.measureText`）。目視で判断しない
5. **表で報告**（下のテンプレ）

### 報告テンプレ

| 箇所 | 項目 | カンプ | 実装 | 判定 |
|---|---|---|---|---|
| 200+ | 書体 | SF Pro Text | SF Pro Display | ❌ |
| 200+ | ウェイト | 100 | 100 | ✅ |

**取れなかった項目は「—（取得できず／こう仮定）」と書いて表に残す。省略しない。**

### 実測に使うコード

```js
// 書体が本当に効いているかは、文字幅を測って特定する
const cv = document.createElement('canvas').getContext('2d');
const w = f => { cv.font = `100 120px ${f}`; return cv.measureText('200+').width; };
w(getComputedStyle(document.documentElement).getPropertyValue('--font-en')); // 実際に使われる書体
w("'SF Pro Text'");     // カンプの指定 → 一致すれば正しい

// まとめて確認
const s = getComputedStyle(document.querySelector('.target'));
({ font: s.fontFamily, w: s.fontWeight, size: s.fontSize, lh: s.lineHeight,
   ls: s.letterSpacing, pad: s.padding, radius: s.borderRadius,
   shadow: s.boxShadow, gap: s.gap, color: s.color });
```

## 4. カンプが完璧でない時（よくある）

カンプは人が作るものなので、矛盾・抜け・ミスが必ずある。
**勝手に直さない。勝手に無視もしない。気づいた時点で言う。**

| 状況 | どうするか |
|---|---|
| **似た要素で値がバラバラ**（padding が 32 / 33 / 34 など） | 「揃えますか？それとも実測通り？」と**確認**。揃えるなら基準値を提案 |
| **カンプに無い状態**（hover / focus / 押下 / 空 / エラー / 読み込み中） | 「カンプに無いので、こう補完します」と**明示して提案** |
| **レスポンシブの指定が無い** | ブレークポイントと考え方を**提案してから**作る |
| **明らかなミス**（はみ出し・重なり・誤字・色の不統一） | **指摘して確認**。黙って直すと意図を消す可能性がある |
| **カンプと絵コンテ/口頭指示が食い違う** | 両方を並べて示し、**どちらを採るか確認** |
| **カンプが更新されていた** | 差分を報告してから追従。ノードIDが新しい番号なら追加・変更のサイン |

### 指示（プロンプト）が曖昧な時も同じ

勝手に狭めない・勝手に広げない。
**「こう解釈しました。違ったら言ってください」と前提を明示して進める。**
判断が分かれて手戻りが大きい所だけ、作る前に聞く。

---

## 5. 改善提案も仕事のうち

言われたことをなぞるだけでなく、気づいたら**提案する**。

- 値がバラついている → デザイントークンに寄せる提案
- 同じパーツが少しずつ違う → 共通化の提案
- アクセシビリティ上の問題（コントラスト不足・文字が小さすぎる）→ 指摘
- 実装上むしろ良くなる代替案がある → 選択肢として出す（勝手に採用はしない）

## 6. 作業開始時のチェックリスト

- [ ] カンプの URL とノードIDを控えたか
- [ ] **スペック表をコードより先に作った**か（0章・例外なし）
- [ ] **前回から更新されていないか**確認したか
- [ ] 該当セクションの**全ノードを列挙**したか
- [ ] フォント・色・余白・角丸・影を `get_design_context` で**取得**したか（推測していないか）
- [ ] 取れなかった項目を**書き出した**か
- [ ] 実装後に**実測で照合**し、**表で報告**したか
- [ ] カンプの矛盾・抜けを**報告**したか
