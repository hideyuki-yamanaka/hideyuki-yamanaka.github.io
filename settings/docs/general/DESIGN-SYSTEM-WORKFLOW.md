## この作業の目的（先に合意すること）

**「見た目を変える作業」ではない。** 同じ見た目のまま、**値に名前を付けて出どころを1か所にする**作業。

| やること | やらないこと |
|---|---|
| 散らばった値を数え、似たものを寄せる | 見た目を良くする（それは別の作業） |
| 値に名前を付けて1か所に集める | 名前を付けずに整理だけする |
| 本番で使う値だけを残す | 比較検討（mock）の値まで載せる |

**着手前に必ずヒデさんに確認すること**
1. 「見た目は変えません。ただし**似た値は寄せるので1〜2px動く箇所は出ます**」→ これでいいか
2. 統合の優先順（下記フェーズ2）をこちらで決めていいか、都度確認するか

## フェーズ1: 洗い出し（棚卸し）

### 1-1. 実装から生の値を全部拾う

**目視で探さない。数えて出す。** 下のコマンドはそのまま動く（`app` `components` は対象ディレクトリに読み替え）。

```bash
# 色（HEX）を使用回数の多い順に
grep -rhoE '#[0-9a-fA-F]{6}\b' app components --include='*.tsx' --include='*.css' \
  | tr 'a-f' 'A-F' | sort | uniq -c | sort -rn

# Tailwind の任意値クラス [13px] など＝トークン化できていない印
grep -rhoE '\[[0-9.]+(px|rem|%)\]' app components --include='*.tsx' | sort | uniq -c | sort -rn

# イージング（見分けのつかない曲線が増殖しがち）
grep -rhoE 'cubic-bezier\([^)]*\)' app components --include='*.tsx' --include='*.css' | sort | uniq -c | sort -rn

# 角丸 / ブラー / 影 / 不透明度 / 秒数
grep -rhoE 'rounded-\[?[0-9a-z.]+\]?' app components --include='*.tsx' | sort | uniq -c | sort -rn
grep -rhoE 'blur-\[?[0-9a-z.]+\]?'    app components --include='*.tsx' | sort | uniq -c | sort -rn
grep -rhoE 'shadow-\[?[^ "\x27]+\]?'  app components --include='*.tsx' | sort | uniq -c | sort -rn
grep -rhoE '/(5|10|20|25|30|40|50|60|70|75|80|90|95)\b' app components --include='*.tsx' | sort | uniq -c | sort -rn
grep -rhoE '(duration|delay)[-:] ?[0-9.]+' app components --include='*.tsx' | sort | uniq -c | sort -rn

# ある値がどのファイルに出るか
grep -rlni '#0070c9' app components --include='*.tsx'
```

### 1-2. ⚠️ 本番と比較検討（mock）を必ず分けて数える

**ここを分けないと数字が10倍ズレる。** 実例（abashiri-site）:

| 対象 | HEX の出現数 |
|---|---|
| 全部（mock 込み） | **68 回** |
| 本番だけ（`--exclude-dir=mock`） | **5 回** |

比較検討ページの値まで統合対象にすると、「使っていない値を大事に扱う」ことになる。

```bash
grep -rhoE '#[0-9a-fA-F]{6}\b' app components --include='*.tsx' --exclude-dir=mock | sort | uniq -c | sort -rn
```

### 1-3. カンプ側からも数える

実装だけ見ていると「**カンプにあって実装に無いもの**」は絶対に見つからない。
Figma に「デザインシステム」の板があるならそれを、無ければ対象セクションの全ノードを
`get_design_context` で取る（→ [DESIGN-SYSTEM-RULES.md](DESIGN-SYSTEM-RULES.md) 3章）。

### 1-4. 洗い出し表を出して、ここで一度止まる 🔴

| 種類 | いま何個 | 内訳（使用回数つき） | 統合案 |
|---|---|---|---|
| カラー | 17 | `#0070C9`×68 / `#0080E4`×1 … | 12 へ |
| 角丸 | 6 | 12/24/30/60/290 … | 5 へ |
| イージング | 3 | `(0.33,1,0.68,1)`×5 / `(0.25,1,0.35,1)`×1 … | 2 へ |

**この表を見せてから統合に入る。** 勝手に統合しない。

## フェーズ2: 統合（似た値を寄せる）

判断は次の順。**理由を必ず1行で書く**（後から「なぜ消したか」を追えるように）。

| 優先順 | 基準 | 例（実例より） |
|---|---|---|
| 1 | **使用1か所の値は、近い値へ寄せる** | `#CCE4FA`（1か所）→ `#B6DAFC`（4か所） |
| 2 | **並べても見分けがつかないものは統合** | 緑2色 → 40%で重ねると差が消えるので1つに |
| 3 | **画面に出る回数が多い方に寄せる** | 角丸 24px → 30px |
| 4 | **名前を持たせず済むならフィルタで済ます** | ホバー色 → `hover:brightness-110` |
| 5 | **比較検討でしか使っていない値は削除** | バウンドのイージング |

記録の書き方（そのまま完成ドキュメントの「整理の記録」になる）:

| 統合前 | → | 統合先 | 理由 |
|---|---|---|---|
| `#0080E4` | → | `hover:brightness-110` | 使用1か所。名前を持たずフィルタで足りる |

## フェーズ3: 命名（ここが一番あとで効く）

名前は **`カテゴリ_なにか`**。決め方は2通りだけ。

| 決め方 | 対象 | 例 |
|---|---|---|
| **カテゴリ + 値** | 大きさで決まるもの（文字・角丸・ブラー・余白・線・不透明度） | `Title_48px` `Radius_30px` `Blur_16px` |
| **カテゴリ + 役割** | 意味で決まるもの（色・影・イージング） | `Brand_Primary` `Shadow_Modal` `Ease_Standard` |

- **色を見た目で名付けない。** `Blue_500` ではなく `Brand_Primary`。
  → 色を変えても名前が生き残る（見た目で名付けると、赤くした瞬間に `Blue_500` が嘘になる）
- CSS 変数名はフレームワークの名前空間に乗せる（Tailwind なら `--color-*` → `bg-*`、`--radius-*` → `rounded-*`）。
  **ドキュメント上の名前と1対1**にする
- その案件ならではの言葉（`botto` / `tamannee` など）はアセット名・コンポーネント名にそのまま残してよい

## フェーズ4: 実装をトークン駆動に置き換える

1. **唯一の出どころを決める**（Tailwind v4 なら `app/globals.css` の `@theme` ブロック）
2. そこに名前付きで全部定義し、**本番コンポーネントから生の HEX・px を一掃**する
3. 任意値クラス（`[13px]`）をやめ、スケールに乗せる
4. **二重管理を潰す**（変数があるのにコンポーネントが同じ値を直書き、が実際にあった）

⚠️ **置換は一気にやらない。** 種類ごと（色 → 角丸 → 文字 → 影 …）に区切って、
1種類ごとに画面を確認する。まとめて置換して巻き添えを出す事故が実際に起きている
（→ CLAUDE.md 手戻り防止ルール5）。

### この時に必ず見つかる不具合（実例）

- **フォントウェイトの指定漏れ**: 1か所だけ `font-weight` 未指定で、読み込んでいないウェイトを要求していた
- **影の色がフレームワーク既定の黒のまま**: ブランドの色に統一されていなかった

見つけたら**直してよい**が、**「ついでに直した」と報告に必ず書く**。

## フェーズ5: 比較検討（mock）の値を本番から追い出す

- 3案比較のための値を**本番コンポーネントに残さない**。mock ページ側に持たせる
- 本番には**採用案だけ**を直接書く
- コンポーネント名から `Mock` を外す（`MockNav` → `GlobalNav`）

## フェーズ6: ドキュメント化

**載せるのは本番の画面で実際に使っている値だけ。** 章立てはこの順が読みやすい。

```
0. このドキュメントの立ち位置（値の唯一の出どころはどこか／ずれたらコードが正）
   命名の考え方
1. カラー   2. テキスト   3. 角丸   4. 余白   5. シャドウ   6. ブラー
7. モーション（① 速さ ② 間 ③ 繰り返し）
8. 線と不透明度   9. コンポーネント一覧
10. 整理の記録（統合前 → 統合先 → 理由 ／ 過去に直した不具合）
11. 戻したい時（退避ブランチ）
12. これから値を足す時
```

**各値に「どこで使うか」を1行で添える**（`Radius_30px  板の中の面：タブレット内側・プロモカード・ダイアログ`）。
これが無いと、次に足す人が同じ値を作り直す。

---

## フェーズ7: 運用ルール（完成後）

1. 唯一の出どころ（`@theme` など）に**名前を付けて**足す
2. コンポーネントではその名前だけを使う
3. ドキュメントと Figma の板を**同じタイミングで**更新する

> コンポーネントに px や HEX を直接書きたくなったら、それは**「名前が足りない」というサイン**。
> 比較検討のための値なら、名前を付けず mock 側に置く。
